### Shard-size update (2026-05-13)

User reports **shards are ~1 TB each** (not 100-200 GB as initially estimated). NVMe ceiling on largest Arbutus cm flavor is **560 GB** (cm16), not 1 TB.

**Big correction from `/home/michael/Projects/AMI/ami-devops/docs/ARBUTUS_AZURE_BENCHMARKS.md` (Fieldguide R0 perf gate, 2026-05-12):**

- Workspace VM `ami-workspace-02-gpu` is flavor **`g1-24gb-c6-70gb-250`** — 6 vCPU, 70 GB RAM, **250 GB qemu virtio (Cinder-tier, NOT local NVMe)**, ~2.6K randread IOPS, ~380 µs avg latency.
- "g1 GPU flavors do NOT have local NVMe. GPU is the value prop; treat g1 storage as ephemeral scratch."
- cm class HAS NVMe but max is cm16 = **560 GB** (cm8 = 280, cm4 = 140). No GPU on cm.
- cb class has bigger ephemeral SSD (cb32 = 1,120 GB) but **NOT NVMe + IOPS degraded 19× over 3 days on db-01**. No GPU on cb.
- p class is durable Cinder, 97 randread IOPS — useless for random image reads.

**Implication:** No single flavor combines (a) GPU, (b) ≥1 TB local fast storage. Single-host NVMe staging is structurally impossible for 1 TB shards.

For single-pass inference (each image read once), local cache doesn't help — no second reads to serve from NVMe. **Real lever is parallel S3 reads OR a two-VM architecture**, not single-host caching.

### Candidate paths (with 1 TB shards + g1 has no NVMe)

| Path | Approach | Est. throughput | Wall-time | Notes |
|---|---|---|---|---|
| **A** — Direct S3 + aioboto3 on g1 GPU VM | Skip FUSE entirely; 100-300 concurrent S3 GETs by key | 200-500 img/s | ~10 hr | Requires S3 keys flat in bucket, not only inside .sqfs |
| **B** — Per-bucket extraction to g1 Cinder | `unsquashfs -d /mnt/extract task_N.sqfs <bucket>/`; rotate batches that fit 250 GB Cinder | extract S3-bound; inference at Cinder speed (~2.6K IOPS) | 20-40 hr | Cinder is slow for random reads |
| **C** — mountpoint-s3 prefetch + DataLoader on g1 | Tune mountpoint-s3 (`--prefetcher-max-memory-size 8GB --network-throughput-gbps 10`); squashfuse over it; DataLoader `num_workers=32, prefetch_factor=8` | 100-300 img/s | 10-30 hr | No staging needed, least-code |
| **D** — Two-VM pipeline: cm16 stager + g1 GPU | cm16 (560 GB NVMe) rsync's a shard at a time from S3, exports via NFS/SSHFS over the 0.345 ms intra-VLAN; g1 reads from network mount | network-bound on intra-VLAN; could hit ~500 MB/s | 8-15 hr | Two VMs to manage; rsync overlap with inference |
| **E** — cb32 standalone (no GPU, CPU inference) | 1,120 GB SSD fits a shard; YOLO26 CPU inference | ~5-15 img/s CPU | 8-25 days | Falls way short of 1-day target |
| **F** — Pull lower-res variant from S3 | If a "medium" variant exists, total dataset shrinks ~5-10× | depends | depends | Need to confirm variant exists |
| **G** — Re-shard finer (one-time cost) | Build new 100-GB shards from existing 1-TB ones | one-time S3 read of 10 TB | weeks of S3 read | Defeats purpose |

**Best candidates:** A (direct S3) or D (two-VM cm16 stager + g1 GPU). C (mountpoint-s3 tuned) is the no-new-infra fallback.

A is cleanest **if** the underlying S3 bucket has flat image objects (not only .sqfs files). D is most predictable but adds operational complexity.
